## Description

Implement Google OAuth 2.0 authentication flow with authorization code exchange, token verification, and automatic user creation. Support linking existing accounts by email and populate user profile from Google data.

**Business Value**: Reduces authentication friction by allowing users to sign up/login with existing Google accounts, improving conversion and reducing password fatigue. Supports seamless account linking for returning users.

**Reference**: PRD section 2.5 (OAuth Integration), Story 3.8 foundation

## Acceptance Criteria

**Authorization Flow:**
- [ ] Given user clicks "Sign in with Google" button, When consent screen loads, Then authorization code is obtained
- [ ] Given authorization code from callback, When exchanged with Google API, Then valid ID token is received
- [ ] Given ID token from Google, When signature is verified with Google public keys, Then token is trusted

**User Management:**
- [ ] Given new user authorizing for first time, When email is verified with Google, Then user account is auto-created
- [ ] Given returning user with existing email, When authorizing with Google, Then account is linked (no duplicate created)
- [ ] Given successful OAuth, When user profile fetched from Google, Then name, avatar, and email_verified are populated

**Session & Token Management:**
- [ ] Given successful OAuth login, When tokens are issued, Then access token (15m) and refresh token (7d) are generated
- [ ] Given refresh token, When set in response, Then httpOnly cookie is used with secure/sameSite=strict flags
- [ ] Given successful OAuth, When redirected to home, Then accessToken is in URL query param and captured client-side

**Error Handling & Logging:**
- [ ] Given invalid or expired authorization code, When processed, Then 400 response with error message is returned
- [ ] Given Google API error (rate limit, connectivity), When encountered, Then 500 response with logged error is returned
- [ ] Given OAuth attempt (success or failure), When processed, Then Winston logger records event with userId/timestamp

**Code Quality:**
- [ ] Given implementation complete, When TypeScript compiled, Then 0 errors are reported
- [ ] Given package.json updated, When dependencies installed, Then google-auth-library is available

## Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| Google API rate limits during peak traffic | Medium | Implement exponential backoff, cache public keys locally, monitor quota usage |
| Credential exposure (client_id, secret, callback URL) | High | Use environment variables, never commit credentials, rotate secrets regularly, use GitHub Secrets |
| Token redirect via URL query param (accessToken exposed in browser history) | Medium | Use short-lived tokens (15m), consider POST redirect instead, educate users on security |
| Email verification bypass (trusting Google's emailVerified flag) | Low | Validate that Google returned emailVerified=true, re-verify in Story 3.10, audit logs for suspicious patterns |
| Account linking collision (two Google accounts with same email) | Low | Enforce email uniqueness constraint, log linking attempts, alert on suspicious activity |
