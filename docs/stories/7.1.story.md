## Technical Details

### Cache Key Naming Strategy

```
article:{id}              # Single article by ID
article:slug:{slug}       # Single article by slug
category:all              # All categories
search:{query_hash}       # Search results (hash of query string)
session:{userId}          # Session data
```

### TTL Strategy

| Data Type | TTL | Invalidation Trigger |
|-----------|-----|---------------------|
| Articles | 1 hour | article create/update/delete |
| Categories | 24 hours | category create/update/delete |
| Search results | 1 hour | search_index rebuild |
| Sessions | 7 days | logout, token expiry |

### Cache Warm-up

- Run on server startup
- Load top 100 articles (by views/recency)
- Load all categories
- Log warm-up metrics

### Error Handling

- If Redis unavailable: fall back to database queries
- Log all Redis errors for monitoring
- Implement connection health checks
- Retry failed operations (exponential backoff)

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Redis connection failure | App falls back to slow DB queries | Implement fallback to database, connection retry logic, health checks |
| Cache invalidation bug | Stale data served to users | Comprehensive testing, manual verification, conservative TTL values |
| Memory issues (Redis fills) | Redis eviction or OOM | Set maxmemory policy (allkeys-lru), monitor with redis-cli INFO memory |
| Cache stampede (many requests to expired key) | Database spike after cache expiry | Implement cache-aside pattern with probabilistic early expiry |
| Development complexity | Harder to debug caching issues | Add cache debug mode (log all operations), redis-cli CLI monitoring |
