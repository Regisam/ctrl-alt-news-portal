## Description

Implement Redis caching layer to improve application performance. Cache frequently accessed data (articles, users, comments, categories) with configurable TTL and cache invalidation strategies. Reduce database queries and improve API response times from ~200-500ms to <100ms for cached endpoints.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Redis connection failure | App falls back to slow DB queries | Implement fallback to database, health checks, connection retry logic |
| Cache invalidation bug | Stale data served to users | Comprehensive testing, manual verification, conservative TTL values |
| Memory issues (Redis fills) | Redis eviction or OOM | Set maxmemory policy (allkeys-lru), monitor redis-cli INFO memory |
| Cache stampede (many requests to expired key) | Database spike after cache expiry | Implement cache-aside pattern with locks or probabilistic expiry |
| Development complexity | Harder to debug caching issues | Add cache debug mode (log all cache operations), redis-cli monitoring |

---

## Notes

- Start with simple read-through cache, upgrade to write-through if needed
- Use cache-aside (lazy loading) pattern initially
- Conservative TTL values first, optimize based on metrics
- Redis should be in same network as Express (low latency)
- Plan for cache invalidation on article updates, comment posts
- Consider cache warming for homepage data

## Technical Design

### CacheService API

```typescript
interface CacheService {
  get<T>(key: string): Promise<T | null>
  set<T>(key: string, value: T, ttlSeconds?: number): Promise<void>
  invalidate(pattern: string): Promise<void>
  clear(): Promise<void>
  getMetrics(): { hits: number; misses: number; hitRate: number }
}
```

### Cache Key Naming Convention

```
articles:list:page:1
articles:detail:123
categories:all
users:profile:456
comments:article:789
search:query:keyword
```

### Invalidation Rules

- `articles:*` invalidated on article create/update/delete
- `categories:*` invalidated on category create/update
- `users:profile:*` invalidated on user update
- `comments:*` invalidated on comment create/delete
- `search:*` invalidated on any article change
